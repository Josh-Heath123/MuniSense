## The domain model

### Layers

`munisense.domain` is pure: no I/O, no clock, no imports outside the domain, an allow-list of standard-library modules and Pydantic v2 in strict mode (ADR-0004; import-linter rules 1, 1b, 1c and the purity test). Inside it:

```text
billing   ->  tariffs  ->  money  ->  citations | periods        (arrows: "may import")
base.py   (DomainModel: strict, frozen, extra fields refused; refuses any float or
           unchecked decimal field when a model is defined)
```

### Main types

| Layer | Type | What it is |
| --- | --- | --- |
| `money` | `ExactDecimal` | A `Decimal` that is finite and exact (at most 60 digits). In JSON it must be a string of the form `-?[0-9]{1,15}(\.[0-9]{1,12})?`; JSON numbers, floats, ints and bools are refused |
| | `exact()` | A decimal context that raises instead of rounding (Inexact, Rounded and seven other signals are traps). All arithmetic runs inside it |
| | `Money` | Rand amount; `+`, `-`, `* Decimal`, `sum`, `quantised(Quantisation)`. Never rounds by itself; a result too wide to hold exactly is a domain error (`Money.of`) |
| | `Rate`, `RateUnit` | A rate as printed (c/kWh, R/kWh, R/day, R/month) and its exact canonical form (cents shifted by `scaleb`, not divided); `charge(quantity) -> Money` |
| | `Quantisation` | A power-of-ten step (1 to 1E-12) and one of six modes; `apply` and an exact `divide` (Fraction-based, for prepaid rand-to-kWh later). The **only** rounding in the domain |
| | `RoundingPolicy` | Names every ADR-0005 rounding point: `line_amount`, `vat_application` (per line or on the subtotal), `vat_amount`, `total`, `prepaid_kwh`. Each is a `Quantisation` or `None` (not rounded). Has its own status and evidence |
| | `VatRate`, `VatTable` | Cited percentage and cited start/end dates; contiguous entries; `rate_for(period)` refuses a period with no rate or across a change |
| `citations` | `Citation` | Document SHA-256, page, locator (table/row), the **original printed text** |
| | `Cited[T]` | A value with a required citation and a status |
| | `Verified` / `Estimated` / `UserProvided` | Statuses. `Verified` needs a human verifier handle, method, date and a `TextCheck` (`passed` or `no_text_layer`). `Estimated` needs a reason. `UserProvided` names a fixed source category (no free text) |
| | `cited_statuses`, `weakest_kind` | Walk any model and collect every status; summarise to the weakest |
| `periods` | `DateRange` | Half-open `[start, end)`, never empty; `days`, `covers`, `is_whole_calendar_month` |
| `tariffs` | `FixedCharge` | R/day or R/month |
| | `FlatEnergy` | One rate per kWh |
| | `BlockEnergy`, `Block` | 1 to 20 blocks; each block has a cited upper threshold (per calendar month) and a cited rate; the last is open-ended; thresholds strictly increase |
| | `TariffVersion` | Supplier, tariff code, customer class (catalogue keys); cited printed name, applicability, effective dates (half-open, open end allowed) and price basis (excluding or including VAT); the rounding policy; 1 to 30 named components in order |
| `billing` | `PeriodTotal`, `TimeOfUseBuckets` | Consumption profile (a union read by `kind`); only `PeriodTotal` is evaluated before P4 |
| | `calculate_bill` | `(version, period, consumption, vat_table) -> Bill` or a `DomainError` |
| | `Bill`, `LineItem`, `Source`, `BillWarning` | Lines with quantity, printed rate, amount, VAT treatment, optional per-line VAT and **sources by role** (rate, lower/upper threshold, label, VAT treatment), each with citation and status; subtotal, VAT, total, weakest status, rounding policy and its status, warnings |

Every component and the version carry `schema_version: 1`. Components are read by `kind` (a discriminated union), so a JSON file names what each component is.

### Per-value citations and statuses

- **Every value is a `Cited[T]`**: a rate, a threshold, a label, a VAT treatment, a date, the price basis, the printed name. The citation is required by the type, so a value without one cannot be built (`UnparameterisedCitedError` also refuses a bare `Cited`).
- **Status of anything = the weakest status of every cited value inside it**, found by walking every field (`cited_statuses`), not by listing fields. This was proven by weakening each of 16 value positions of a version in turn (`test_one_weaker_value_anywhere_weakens_the_summary`), and 12 positions of a bill (`test_one_weaker_value_makes_the_bill_warn`).
- **The order is user-provided < estimated < verified (W8).** It is applied in one place (`weakest_kind`).
- **A bill's status** is the weakest of each line's values, every header value of the version, and the VAT rate. Values of components that produced no line (for example energy at zero use) do not count, because the bill does not depend on them.
- **Warnings**: any non-verified value gives `unverified_values`; a non-verified rounding policy gives `unverified_rounding_policy` ("cent-level differences from a real bill are possible"). Each warning is proven to appear on its own.
- **A line names its sources by role**, so a disputed line can be traced to the exact printed text it used: for a block, the rate, both thresholds that bound it, the label and the VAT treatment.

### How the pieces plug in

**Rounding policies (built).** The engine never rounds on its own. It quantises each line at `line_amount`, applies VAT per line or once on the standard-rated subtotal (`vat_application`) and quantises it at `vat_amount`, and quantises the total at `total`. `None` at a point means "not rounded there". A purity test refuses `.quantize` anywhere outside `money/rounding.py`. The policy is data on the version, with its own status: Ekurhuleni's is `estimated` until learnt from real bills or receipts (P3). A test with a different step and mode at each point proves that each point uses its own quantisation (point-swap mutants are killed).

**Seasons (P1-12, after this checkpoint).** Proposed: a `SeasonalEnergy` component holding a **season calendar in data** (month-day ranges covering the year without gaps or overlaps, refused otherwise), with a cited rate (flat or blocks) per season. The engine evaluates it only for a period inside one season; a period across a season boundary goes through period splitting. Ekurhuleni Tariff B prints a high-demand (June to August) and a low-demand (September to May) energy rate. Both are `R3.37,00` in 2026/27, so P1-9 transcribed one flat rate citing both cells. It becomes a seasonal component with two citations when P1-12 lands. Until then, bills in both seasons use the same value through the same code path, so **seasons are not exercised yet**.

**Period splitting (P1-13).** Proposed: a period that crosses a version change, a season boundary or a VAT change is split into sub-periods. Each sub-period is calculated with the existing engine, and fixed charges and block thresholds are apportioned by a **pro-rating policy in data** (for example by days), `estimated` until real bills confirm it. Today the engine **refuses** any period that is not one calendar month when the tariff has monthly values (`NonMonthlyPeriodError`). The schedule itself says "The cross-over from existing tariffs to new tariffs will be billed pro rata" (page 1). Open design point: ADR-0005 names no rounding point for pro-rating, and pro-rated quotients (R109.78 x 17/31) do not terminate, so exact arithmetic refuses them. P1-13 needs a `pro_rating` quantisation point, which changes an Accepted ADR (question Q4 below).

**Prepaid (P1-14, P1-15).** Proposed: the inverse of the forward engine over the same components. Given a rand amount and the month's earlier purchases, find the kWh at which the cost of (earlier kWh + new kWh) minus the cost of the earlier kWh equals the amount (VAT-inclusive). Using the same components means a purchase and a bill can never disagree. The kWh are rounded at the policy's `prepaid_kwh` point using the exact `Quantisation.divide`. Block reset (calendar month, or another rule) and the treatment of fixed charges on prepaid are policies in data. For Ekurhuleni Tariff B this is simple: one rate per kWh, no blocks. The open question is the R109.78 monthly basic charge, which the schedule charges "per month, per point of supply" but does not say how a prepaid customer pays (taken from the first purchase of the month, spread over purchases, or billed separately). The owner's real receipts (the parallel track) will answer it. There is also a once-off 40 kWh conversion allocation, "recovered with the first monetary transaction" (page 5).

## Verifying scanned sources (requested, E31)

**The problem.** ADR-0006 makes `verified` need both a deterministic check (the printed text appears verbatim in the extracted text of the cited page, *where the PDF has a text layer*) and a recorded verifier, method and date. "A page without a text layer (a scan) cannot reach `verified` without a human check", and an agent's check does not count. The signed 2026/27 schedule has no text layer on any of its 37 pages, so the P2 automatic check cannot read it. The model is ready for a human check: `Verified` records `text_check: no_text_layer`. What is missing is a decision on how the human check is done.

**What would need checking for Tariff B.** 13 distinct cited values on pages 1 and 4 (name, applicability, two dates, price basis, three labels, two VAT treatments citing the same sentence, two basic charges, and the energy rate counted once for both cells), plus the VAT rate's 2 values in the SARS guide (which has a text layer, so the P2 check can run on them). There is also one interpretation to confirm outside the schedule: that `R3.37,00` means R3.3700/kWh. A vending receipt showing kWh against rand would settle it.

## What was proven

- **Exactness**: no float anywhere. Floats are refused in Python and JSON. Arithmetic is exact or refused. Rounding happens only at named policy points. Evidence: P1-2 and P1-4 tests, the purity test, and property tests whose VAT and subtotal match an independent 200-digit calculation (`test_amounts_and_vat_match_an_independent_calculation`).
- **Provenance**: every value is cited; a status summary cannot miss a value (16 and 12 weakened positions); warnings are proven alone.
- **The engine**: never negative, never falls as use rises, block quantities add up and stay within their blocks (property tests). Extreme values end in a bill or a domain error. Refusals are tested.
- **Ekurhuleni Tariff B**: six bills to the cent with written hand calculations, recalculated independently by the tariff-verifier. Every value MATCHes the page (agent check, not `verified`).

## What was NOT verified, and why

- **No Ekurhuleni value is `verified`.** The schedule is a scan (see the section above), and ADR-0006 needs a human and the owner's check. The tariff-verifier's MATCH verdicts are evidence only.
- **The reading `R3.37,00` = R3.3700/kWh** is inferred from format and magnitude. It is not confirmed against a receipt.
- **Ekurhuleni's rounding** (cents, half up, VAT once on the subtotal) is assumed. It is `estimated` until real bills or receipts are available (P3).
- **Standard VAT rating** of municipal electricity is inferred. The schedule says only "VAT excluded".
- **The VAT rate** is cited to a SARS guide (January 2025) plus Act 3 of 2026, not to the VAT Act itself, which SARS does not offer as a download. "No end date" means "no known end as of 2026-11-18".
- **Seasons, period splitting and prepaid** are not built (P1-12 to P1-15).
- **Mutation testing** has not been run yet (P1-15).

## Deviations from the roadmap or ADRs

- **P1-9's "example that crosses a block threshold" was dropped.** Tariff B has no blocks (E32, owner decision). Block thresholds stay proven with fixture tariffs (P1-7).
- **The roadmap's P1 proof includes a hand-checked prepaid purchase that crosses a block threshold, using Ekurhuleni 2026/27 figures.** That cannot be done with Ekurhuleni: no residential tariff has blocks in 2026/27. A.1 has 50 free kWh then one rate, governed by the separate FBE policy. Proposal: prove block-crossing purchases with fixture tariffs, and use Ekurhuleni Tariff B for the month-of-purchases example (question Q6).
- **The Ekurhuleni transcription is under `data/drafts/`, not `data/tariffs/`.** `data/tariffs/` is defined as reviewed and published; nothing is reviewed until P3.
- **ADR-0005 needs a pro-rating rounding point** before P1-13 (question Q4). No ADR has been changed.

## Risks and concerns

- **Owner time for verification grows with tariffs and years.** Every Ekurhuleni schedule seen so far is scanned. The choice in the scanned-sources section sets the long-run cost.
- **Prepaid basic charge.** If the City recovers the monthly basic charge from prepaid purchases in a way the schedule does not state, the prepaid calculation cannot be exact until a receipt shows how. This is the single biggest unknown for the P3 pilot.
- **Earlier versions with different figures are online.** Budget Annexure F differs from the signed copy for Tariff B. Anyone comparing against the budget papers will see "wrong" numbers. Citing by SHA-256 protects us, but the explanation belongs in user-facing text later.
- **Values can change mid-year.** Page 37 says Eskom structural changes "will be effected immediately". Tariff versions must be able to end early, and they can (the effective end is cited data).

# Security and privacy

> Technical controls do not make MuniSense legally compliant. This document lists controls that exist, risks, and **items that need formal verification by a qualified person**. Never describe the system as "POPIA-compliant".

## Principles

- Collect nothing that is not needed. The MVP stores no personal information (ADR-0008).
- Secrets only in environment variables (`.env` locally; never committed).
- Least privilege for database roles, API keys and staff accounts.
- Validate every external input with types and size limits.
- Log metadata, never bodies or personal information.

| Exact-decimal input limits in the domain (`ExactDecimal`): floats, ints and bools refused in Python and JSON; JSON strings must match a strict ASCII grammar (`-?digits[.digits]`, at most 15 integer digits and 12 decimals; no exponents, whitespace, underscores or non-ASCII digits); Python values must be finite and fit 60 significant digits. Validation messages are fixed text and never echo the input. Arithmetic runs in a context that raises domain errors on rounding, division by zero, overflow, invalid operations and floats. `model_construct` and `model_copy` (which skip validation) are banned in the domain by `test_domain_purity.py`. Every `DomainModel` refuses, when it is complete (also after a rebuild), any compiled schema path that could accept a float: a bare `Decimal`, a `float` or an untyped field, also through aliases, forward references, dataclasses, plain models and generic parameters; an unparameterised `Cited` refuses to validate. Free-text provenance fields refuse control characters and are bounded in length. Pydantic validation errors do not repeat input **values** in `str(exc)` (`hide_input_in_errors`, set on every `DomainModel`), but they do print **field paths**, which can be keys a client chose (any length, control characters included), and `exc.errors()` always holds the raw input: neither may ever be shown or logged. For consumption JSON this is closed in `services.consumption.parse_consumption_json` (P4-4): no `ValidationError` leaves it; it raises only `ConsumptionJsonError`, with fixed text and Pydantic's error type codes, raised outside the `except` block so no exception chain carries the input (tested with names planted in values, keys and field names). P5 shows only stable codes and logs messages, never exception chains. Rounding steps are bounded (1 to 1E-12), VAT tables to 100 entries, rounding-policy evidence to 100 citations. Consumption: kWh not negative; time-of-use input gives kWh used (one to three entries) and exported (none to three) keyed by the three period names `peak`, `standard` and `off_peak` (P4-4), so at most six figures; a period may be exported only if it is also given as used, and an absent period is never read as zero use (P4-7 refuses a profile that leaves out a period of the calendar). `munisense.services.consumption.parse_consumption_json`, which interfaces must use to read consumption JSON, refuses a key given twice anywhere in the JSON (Pydantic alone keeps the last of two equal keys), in linear time, and turns an unknown profile kind (which Pydantic names in its message) into a fixed-text refusal; it raises only `ConsumptionJsonError` (fixed text and error type codes; no paths, values or chained exception). That interfaces use it is a convention until P5 adds a check. Time-of-use calendars (tariff data, P4-5, P4-6): at most 12 seasons, one schedule per season and day type, 48 ranges a day; holiday lists at most 100 dates, in date order, each inside a cited coverage window that covers every day of its version (which must have an end date) and at most 731 days, each treated as a Saturday or a Sunday; a day outside the window is refused with fixed text (it may come from a consumer's readings). | P1, P4 | built (P1-2, P1-3, P4-4, P4-6); tested in `tests/unit/domain/` and `tests/unit/services/` |

| PDF parsing isolation for the citation check (`src/munisense/ingestion/citation_check.py`, `pdf_text.py`). The parent opens the file without following symlinks or blocking, refuses anything that is not a regular file (checked on the open descriptor), checks the size (64 MiB) and the SHA-256 against the source manifest, and sends exactly those bytes to the child on standard input; the child opens no file by name. The child is `python -I` with an empty environment and `/` as working directory, and its first act is to set hard limits on itself: address space 2 GiB, CPU 120 s, file size 0 (no file content can be written), core dumps 0, 64 file descriptors; the parent adds a 300 s wall-clock timeout and a 64 MiB cap on output. Every pypdf limit is pinned (a test fails if pypdf adds one), and pypdf never runs an external decoder. Measured needs: VAT 404 (the most pages and CPU): 5.7 to 11.4 s of CPU, 45 MB resident, about 64 MB address space, 3.3 MB, 176 pages; Eskom's schedule (the largest file, P4-2): 7.2 MB, 57 pages, 1.5 to 1.6 s of CPU, between 96 and 128 MB of address space. Since P4-2 the data tests also read committed PDFs only through this child, never in the test process. Every failure (wrong file, size, hash, time, CPU, memory, exit code, output shape, page count) fails closed and is tested; child error text is cut and stripped of control characters. **Not covered:** the child is resource-limited, not sandboxed: a pypdf bug that ran code could still read the user's files and use the network (pypdf is pure Python, so the realistic risk is resource exhaustion, which the limits cap). That each listed file is the committed one is checked in CI by `tests/unit/data/test_committed_data.py` (every committed PDF's hash against its manifest), not here. ## Threats to watch (short list)

| Threat | Mitigation |
| --- | --- |
| Wrong tariff data published (the biggest business risk) | Citations, verifier, golden bills, review-and-publish, statuses shown to users |
| Malicious or malformed source documents (PDF parsing) | Built in P2-7: a separate process with time, memory, CPU, size and page limits; only committed, hash-listed files; never execute content; human review of extracted values. A SHA-256 proves which file it is, not that it is safe |
| Secret leakage via commits or logs | gitleaks; guard hooks; log policy |
| Injection (SQL, template) | ORM parameters; auto-escaping templates; no string-built queries |
| API abuse | Keys, rate limits, size limits (P5) |
| Supply-chain compromise | Hash-verified lock; wheels only; 14-day release delay; pip-audit on every locked Python package (not on native libraries bundled inside wheels: checked by hand at gates); owner approval for new packages; pre-commit hooks run locked tools only, and the gitleaks image is pinned by digest and runs without network |
| Claude Code acting destructively | Permission rules, guard hooks (including a block on pushing to `main`), pull requests, CI, the owner approving merges. (GitHub branch protection on private repositories needs a paid plan, so it was not relied on. *Since E52: a GitHub ruleset on `main` requires a pull request and green CI.*) |
| Tampered or swapped source documents | Source PDFs are committed and identified by SHA-256. A deterministic check of citations against the committed file is planned for P2 |

## Needs formal verification before charging money or going to production

- [ ] Legal opinion: may tariff schedules and related municipal and Eskom documents be reused commercially? (Copyright Act s12(8)(a) suggests yes for official administrative texts; confirm.)
- [ ] Legal opinion: terms of use of any website the data comes from.
- [ ] POPIA: register an information officer with the Information Regulator; prepare a PAIA manual.
- [ ] POPIA: privacy notice; lawful basis for each processing activity; retention periods; operator agreements with any hosting provider.
- [ ] POPIA s72: requirements if data is hosted outside South Africa.
- [ ] Terms of service and limitation of liability for calculation errors (Consumer Protection Act and ECTA considerations). Needed before any public calculator (decided at P9).
- [ ] Tax: VAT registration and invoicing requirements once revenue starts (accountant).
- [ ] Trademark and domain checks for the product name.
- [ ] POPIA: whether dated purchase figures linkable to a named person (the owner's observations, `data/observations/`) are personal information, and whether they may stay in git history.
- [ ] Before the repository is ever made public: review whether the committed municipal and Eskom source PDFs may be republished.
- [ ] Before any image or binary is distributed to anyone (not needed while MuniSense runs only as a hosted service): third-party licence notices. psycopg and psycopg-binary are LGPL-3.0 and bundle libxcrypt and keyutils (LGPL-2.1): notices, licence texts and the ability to replace the libraries; Cyrus SASL's licence requires a Carnegie Mellon acknowledgement.
- [ ] Before the repository is ever made public: whether the source PDFs (City of Ekurhuleni, SARS, Eskom) may be redistributed inside a proprietary repository under `LICENSE`, and whether the OFL reading recorded in `docs/assets/FONTS.md` (artwork made with Bodoni Moda is outside the licence's distribution conditions) holds.
- [ ] Before the repository is ever made public: committed public source documents name officials in their text or metadata (for example the Eskom schedule's document author and the tariff book's signed foreword, P4-2). **Needs formal verification:** whether keeping these in git, and later republishing them, is acceptable.
- [ ] Before the repository is ever made public: the owner's own prepaid purchase figures in `data/observations/` (E39) are kept knowingly while the repository is private (E59); decide whether they stay, and whether removing them from git history (a history rewrite) is needed.
- [ ] Before the repository is ever made public: commit metadata shows the owner's private email address on about 87 earlier commits and the owner's names; removing them needs a history rewrite (P1-17 publication-readiness check, `docs/reports/2026-11-18-P1-17-publication-readiness.md`).
